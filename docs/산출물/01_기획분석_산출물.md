## 1. 프로젝트 기획서

### 1.1 프로젝트 개요

| 구분 | 내용 |
| --- | --- |
| 주제 | 실시간 가격 비교 & 할인 추천 (생성형 AI & RPA 결합 주제) |
| 서비스명 | PickTiming(픽타이밍) — 이전 이름 BuyTiming에서 변경 |
| 한 줄 소개 | RPA가 판매처 가격을 1시간 주기로 모으고, 가격 이력으로 구매 적기 점수를 계산하며, Gemini가 판단 근거를 쉬운 말로 설명하는 가격 비교·구매 타이밍 추천 서비스 |
| 핵심 기술 | React·Vite·Tailwind, FastAPI, TiDB, Python RPA, scikit-learn, Google Gemini, Render·EC2·Netlify, GitHub Actions |
| 서비스 주소 | 운영 https://picktiming.onrender.com / 데모 https://picktiming.netlify.app |

### 1.2 선정 배경 및 기획 의도

- 같은 상품도 판매처마다 판매가·배송비가 달라 소비자가 직접 비교·계산해야 합니다.
- 가격은 매일 바뀌기 때문에 현재 최저가를 찾아도 '지금 사도 될까?'라는 판단이 남습니다.
- 현재 가격 중심 비교에서는 구매 시점을 판단할 근거(가격 흐름, 할인 주기)를 소비자가 직접 찾아야 합니다.
- RPA로 가격 이력을 쌓고, 가격 흐름을 점수로 계산하고, Gemini가 이유를 설명하여 '어디서 살지'와 '언제 살지'를 함께 안내합니다.

> 원본의 설문 결과(응답 인원·비율)는 원자료를 확인할 수 없어 근거 자료에서 제외했습니다. 사용자 조사 원자료 확보 후 추가합니다.

### 1.3 개발 목표

| 목표 | 내용 | 확인 방법 |
| --- | --- | --- |
| 가격 수집 자동화 | 등록 판매처 1시간 주기 수집, robots.txt·요청 간격 준수 | 수집 로그(rpa_job_logs), RPA 테스트 |
| 실구매가 비교 | 판매가 + 배송비, 판매처별 비교와 최근 수집 시각 | 비교 API·화면 테스트 |
| 구매 적기 판단 | 0~100 적기 점수와 판정, 이력 30일 미만 판단 보류 | 판정 API 테스트, 모델 F1 기록 |
| 쉬운 설명 | Gemini 조언·상담, 응답 숫자 검증과 대체 응답 | 검증·재요청·대체 테스트 |
| 알림·추천 | 목표가 도달·판정 변화 알림, 오늘의 추천 | 가격 등록 후 알림 생성 테스트 |
| 운영 | Render·EC2 독립 풀스택, CI/CD, 관리자 모니터링 | CI·헬스 체크·관리자 화면 |

> 원본의 정량 목표(관심 상품 300종, 수집 성공률 95%, F1 0.75, 응답 3초)는 측정 보고서가 확보되면 달성 여부를 기록합니다.

### 1.4 주요 기능

| 구분 | 기능 | 설명 |
| --- | --- | --- |
| 사용자 | 회원가입·로그인 | 3단계 가입(약관 → 계정·관심 카테고리 → 첫 알림), 이메일 로그인, 소셜 로그인 연동(키 설정 시) |
| 사용자 | 상품 검색·등록 | 검색·카테고리·추천 필터·정렬, 상품 URL 등록 |
| 사용자 | 실구매가 비교 | 판매처별 판매가·배송비·실구매가, 최저가 강조, 최근 수집 시각 |
| 사용자 | 가격 흐름 차트 | 7·30·90일, 판매처·날짜별 탐색, 기록된 역대 최저가 |
| AI | 구매 적기 판정 | 적기 점수(0~100)와 판정(지금 구매 / 조금 대기 / 기다리기 / 판단 보류) |
| AI (Gemini) | AI 구매 조언·상담 | 분석 수치 기반 설명과 질문 답변, 일일 사용 한도 |
| 사용자 | 관심 상품·알림 | 목표가 등록·수정·삭제, 목표가 도달·판정 변화 알림, 읽음 처리 |
| RPA | 수집·배치 | 매시 가격 수집, 매일 재학습·참가격(설정 시), 매주 리포트 |
| 관리자 | 운영 관리 | 수집 현황·작업 로그, 모델 버전, AI 사용량, 회원 검색·권한 변경 |

> 수집 원칙: robots.txt를 확인할 수 없으면 수집하지 않고, 요청 간격 3초를 지키며, malls.json에 등록된 판매처만 수집합니다. 시연 쇼핑몰 A·B·C는 실제 접속 없이 모의 가격을 생성합니다.

### 1.5 가정 페르소나 (설계용)

| 페르소나 | 특징 | 니즈 |
| --- | --- | --- |
| 직장인 A (30대) | 무선 이어폰·노트북 구매 예정 | 지금 사도 되는지 한눈에 알고 싶음 |

| 맞벌이 가장 C (40대) | 생필품·유아용품 정기 구매 | 가격 흐름과 할인 주기 파악 |

> 페르소나는 화면 설계를 위한 가정이며 조사 결과가 아닙니다. 원본의 실명형 페르소나는 익명형으로 바꾸었습니다.

### 1.6 서비스 흐름

수집(RPA, 1시간) → 저장(TiDB) → 비교(배송비 포함 실구매가) → 판단(적기 점수) → 설명(Gemini) → 알림(목표가·판정 변화)

### 6.2 구매 적기 판단 및 자연어 조언 흐름

- ① 일간 최저 실구매가 계열 생성 → ② 이력 30일 미만이면 판단 보류
- ③ 피처 8종 계산 → ④ 활성 모델의 하락 확률(없으면 규칙 확률)
- ⑤ 점수 = (1 − 하락 확률) × 70 + (1 − 90일 백분위) × 30 → 판정
- ⑥ 분석 사실을 Gemini에 전달 → 응답 숫자 대조 → 불일치 시 1회 재요청 → 실패 시 정해진 설명

### 6.5 보안 구성

- 사용자 API는 JWT, 수집 API는 X-RPA-KEY(hmac 비교)로 인증을 분리합니다.
- 관리자 API는 서버에서 ADMIN 역할을 검사합니다. 테스트 관리자, 본인, 마지막 관리자의 권한 변경을 제한합니다.
- GEMINI_API_KEY는 서버 환경 변수에만 두고 브라우저가 Gemini를 직접 호출하지 않습니다.
- TiDB는 DB_SSL_CA 설정 시 인증서·호스트 이름을 검증하는 TLS로 접속합니다.
- 운영 환경에서 JWT_SECRET·RPA_API_KEY가 비었거나 기본값이면 서버가 시작되지 않습니다.
